# RefactorKit 审核与展示设计：人审结果，不审过程

> 版本：v3.2（2026-10-09）｜ 隶属 [01-设计文档.md](./01-设计文档.md)，对应第 7.7 节
> 需求来源【已确认】："重要的中间步骤和中间结果是我要审核的部分"
> 标注：**【已核对】** 已对照 DSH 2.0.17 构建产物确认 ｜ **【默认假设】** 可推翻

---

## 0. 一页结论

| 问题 | 回答 |
|---|---|
| 和"自主编排"矛盾吗 | 不矛盾。**模型自主的是过程**（怎么查、怎么改、要不要分身）；**人审核的是结果和关键决策**（缺口清单、验收标准、设计取舍、最终交付）。人和代码底线一起"守住结果" |
| 审什么 | 6 个审核点（CP1–CP6），只覆盖改变方向或定义"完成"的节点，不审每一步 |
| 怎么展示 | 4 层，全部使用 DSH 原生界面，**MVP 不写前端代码**：① 审核卡（右侧边栏，可通过 / 修改后通过 / 驳回）② 审核材料文件（Markdown，可直接编辑）③ 代码 diff（DSH 每轮改动卡片）④ 总览看板（单页 HTML） |
| 会不会打断太多 | 每个审核点按策略可设为 `block`（必须审）/ `notify`（展示，不等待）/ `off`；策略可以随风险等级变化。提供 `strict` / `standard` / `light` 三套预设 |
| 改得了吗 | 可以。审核卡里写修改意见，或**直接编辑审核文件**（如契约中的验收断言），插件在通过时重新读取文件 |
| 留痕 | 每次审核的结论、意见、耗时、修改内容都写入账本，作为报告与参赛"真数据"的来源 |

## 1. 审核点（Checkpoints）

| 编号 | 审核点 | 触发时机 | 审核内容 | 为什么值得人审 | 默认策略（standard） |
|---|---|---|---|---|---|
| **CP1** | 缺口清单 | `rk_survey` 首次完成，或 `rk_gaps` 新增 / 拆分 / **标记裁撤** | 新旧对照矩阵、缺口列表、拟裁撤项及理由、完成度口径提示 | 决定"要做什么、不做什么"；**裁撤会直接改变完成度分母**，必须由人拍板 | `block`（裁撤类始终 `block`） |
| **CP2** | 任务契约 | `rk_task_open` | 范围（涉及缺口和目录）、验收断言（命令 + 期望）、**预估风险等级**、实施思路要点、预算 | 定义"什么算完成"，是杠杆最大的一次审核：契约对了，后面全靠底线自动把关 | 预估 L2：`block`；L0/L1：`notify` |
| **CP3** | 关键决策 | 模型调用 `rk_decide`；或任务中首次出现 L2 信号（首次修改迁移脚本、接口签名、鉴权代码） | 决策问题、候选方案（≥2 个）、各自影响、模型推荐及理由 | 表结构、接口签名、兼容策略等一旦定下返工成本高 | `rk_decide`：`block`；首次 L2 信号：`notify` |
| **CP4** | 审查结果 | `rk_review` / 异源分身审查完成 | 审查者模型、发现的问题（blocker / major / minor）、实施者处理计划 | 人可以把某条 finding 标记为"接受风险"或"误报"，也可以追加问题 | `notify`；有 blocker 被模型标为"不修"时 `block` |
| **CP5** | 交付验收 | `rk_task_close` 底线检查**全部通过之后** | 改动摘要、实际风险等级与命中信号、每条断言的证据、仲裁结果、审查结论、越界自检、未完成项 | 最终签收：代码底线只能证明"满足契约"，契约之外的质量（可读性、业务正确性）需要人判断 | 实际 L2：`block`；L1：`notify`；L0：`off` |
| **CP6** | 阻塞上报 | 任务转为 `BLOCKED`（失败上限、预算耗尽） | 卡在哪里、已尝试什么（附证据）、可选出路 | 模型已无法自行推进 | 始终 `block` |

**另外**：不可逆操作（写库、push、装依赖）继续走 DSH 原生**审批**，不归入审核点；二者的界面和语义都不同（审批是"允许这一个动作"，审核是"认可这一个结果"）。

**状态机的变化**：`block` 策略下，CP5 成为 `DONE` 的必要条件：

```text
OPEN ─► (自主工作) ─► 申请关闭 ─► 代码底线 ─通过─► [CP5 人工验收] ─通过─► DONE
                                    │                    │ 修改后通过：带意见回到 OPEN
                                    └─ 不通过：缺哪条     └ 驳回：回到 OPEN，意见写入任务
```

## 2. 展示形式（4 层）

### 2.1 第 1 层：审核卡（需要你做决定的地方）

用 DSH 原生的 `ctx.userQuestions.ask()` 弹出审核卡【已核对】。带 `intent: { kind: 'plan-review', approve }` 的问题会使用与**计划模式相同的审阅界面**：内容在右侧边栏展开，你选择选项或填写意见。

```ts
await ctx.userQuestions.ask({
  agent,                                  // 必须是当前存活的主 agent；子 agent 无法发起（DSH 限制）
  questions: [{
    id: 'cp2-T-07',
    header: 'CP2 任务契约',
    question: 'T-07「数据填报导出」的验收标准是否认可？',
    detail: cardMarkdown,                 // 审核卡正文（见第 3 节模板），一屏以内
    options: [
      { label: '通过', description: '按此契约开工' },
      { label: '修改后通过', description: '我已编辑契约文件或在下方写了意见' },
      { label: '驳回', description: '方向不对，重新拟定' },
    ],
    intent: { kind: 'plan-review', approve: '通过' },
  }],
})
```

- 用户在选项之外填写的文字（`custom`）作为**审核意见**返回给模型，并写入账本。
- `ask()` 等待期间不消耗 token【已核对 dsh-user-questions README】。
- 没有可用应答界面时（例如无人值守运行），`ask()` 失败。此时 `block` 审核点视为**未通过**，任务保持 `OPEN`，不会默认放行。

### 2.2 第 2 层：审核材料文件（需要你细看或动手改的地方）

每个审核点同时生成一份 Markdown 文件，路径固定、可读、可编辑：

```text
.refactorkit/review/
├── CP1-gaps-<日期>.md
└── T-07/
    ├── CP2-contract.md          # ★ 可编辑：断言写在 ```yaml rk-contract 代码块中
    ├── CP3-decision-01.md
    ├── CP4-review-01.md
    ├── CP5-acceptance.md
    └── log.md                   # 本任务所有审核的时间线（自动追加）
```

- 审核卡的 `detail` 只放摘要，并附这份文件的路径；DSH 中 `.md` 文件可以在右侧边栏打开。
- 插件生成文件后通过 DSH `present` 机制给出文件卡片，便于一键打开【已核对 dsh-tool-present】。
- **直接编辑生效**：CP2 契约、CP1 裁撤清单中的结构化部分写在带标记的 YAML 代码块里。选择"修改后通过"时，插件重新读取文件、校验格式，并把修改前后的差异写入 `log.md` 和 journal。格式错误则重新弹卡，并指出错误位置。

### 2.3 第 3 层：代码 diff（看代码改了什么）

不另做。DSH 在每轮结束时显示**改动文件卡片**，每个文件可以打开本轮的 review tab 查看 diff【已核对 dsh-client-ui-deliverables】。CP5 验收卡中列出本任务的文件清单与 `git diff --stat`，并给出查看完整 diff 的命令（`git diff <baseRef>`）。

### 2.4 第 4 层：总览看板（看全局进度）

`rk_report` 生成单页 `.refactorkit/report.html`（无需服务器，双击即开），也可以在 DSH 中让模型"打开进度看板"：

| 区块 | 内容 |
|---|---|
| 进度 | 缺口总数 / 已完成 / 进行中 / 阻塞 / 已裁撤；实测完成度与口径 |
| 待我审核 | 所有处于 `block` 等待中的审核点，按等待时长排序 |
| 任务看板 | 每个任务一行：状态、风险等级、断言通过数、审查结论、审核结论 |
| 审核时间线 | 最近的审核记录：谁（人 / 哪家模型）、结论、意见摘要 |
| 证据与底线 | 被拒关闭的原因统计、环境阻塞、越界与不可逆操作记录 |
| 模型使用 | 分身次数、技能加载次数、各模型 token 用量 |

P2：做成 DSH 右侧边栏的常驻 tab（客户端插件，通过 `ctx.sidebarRightTabs.register` 注册【已核对接口存在】），实时刷新。MVP 只做静态 HTML。

## 4. 策略配置

```yaml
# refactorkit.yaml
review:
  preset: standard                  # strict | standard | light；下面的条目覆盖预设
  checkpoints:
    CP1: { policy: block }
    CP2: { policy: { L0: notify, L1: notify, L2: block } }   # 按预估风险
    CP3: { policy: block, autoOnFirstL2Signal: notify }
    CP4: { policy: notify, blockWhenBlockerWontFix: true }
    CP5: { policy: { L0: off, L1: notify, L2: block } }      # 按实际风险
    CP6: { policy: block }                                   # 不可改为 off
  timeoutPolicy: keep-open          # 无应答时：保持 OPEN，不默认放行（不可改为 auto-approve）
```

| 预设 | CP1 | CP2 | CP3 | CP4 | CP5 | 适用 |
|---|---|---|---|---|---|---|
| `strict` | block | block | block | block | block | 首次使用、演示、高风险系统 |
| `standard` | block | L2 block | block | notify | L2 block | 日常（默认） |
| `light` | block | notify | notify | notify | L2 block | 熟悉后，或批量处理小缺口 |

`notify` 的含义：生成审核文件并在工具结果中提示"已生成 CPx 供审阅"，同时在看板"待我审核"中列出，但**不等待**。你事后在看板中标记"已阅 / 有意见"；若有意见，任务会被重新打开。

**不可放宽的部分**：CP6 不能关闭；`block` 审核点在无应答时不能默认通过；裁撤缺口始终需要 CP1 审核。

## 5. 与自主度档位的关系

| | 自主度档位（free / assisted / guided） | 审核策略（strict / standard / light） |
|---|---|---|
| 管什么 | 给模型多少**过程**建议 | 人在哪些**结果**上签字 |
| 依据 | 模型能力 | 改动风险与使用者信任度 |
| 正交 | 可以任意组合，例如 `free` + `strict`：强模型自由发挥，但每个契约和交付都要人签字 |

## 6. 实现规格

### 6.1 新增与修改的工具

| 工具 | 变化 |
|---|---|
| `rk_decide`（新增） | 模型主动发起 CP3。参数：`taskId`, `question`, `options: Array<{ label, impact, cost }>`（≥2）, `recommend`, `why`。返回：人的选择与意见 |
| `rk_report`（新增） | 生成 `report.html` 并以文件卡片展示。参数：`open?: boolean` |
| `rk_gaps` | `op: retire` 与首次生成清单时触发 CP1 |
| `rk_task_open` | 写入 `CP2-contract.md` 后触发 CP2；`block` 时等待结果；"修改后通过"时重读契约 |
| `rk_review` | 完成后触发 CP4 |
| `rk_task_close` | 底线通过后触发 CP5；`BLOCKED` 时触发 CP6 |

### 6.2 新增模块

```text
src/review/
├── policy.ts        # 根据预设 + 覆盖项 + 风险等级，计算某审核点的策略
├── checkpoint.ts    # runCheckpoint()：写审核文件 → present → 按策略 ask() 或仅提示 → 记录结果
├── templates/       # CP1–CP6 的 detail 与审核文件模板
├── contract-file.ts # 读写审核文件中的 ```yaml rk-contract 代码块，计算修改前后差异
└── report.ts        # 生成 report.html（单文件，内联 CSS/JS，数据内嵌为 JSON）
```

```ts
type Policy = 'block' | 'notify' | 'off'
type CheckpointId = 'CP1' | 'CP2' | 'CP3' | 'CP4' | 'CP5' | 'CP6'

interface CheckpointInput {
  id: CheckpointId
  taskId?: string
  title: string                  // 审核卡 question
  detail: string                 // 一屏摘要（Markdown）
  file: string                   // 审核文件相对路径
  fileContent: string
  options?: string[]             // 默认 ['通过','修改后通过','驳回']
  risk?: 'L0' | 'L1' | 'L2'      // 用于策略计算
}

interface HumanReview {
  checkpoint: CheckpointId
  taskId?: string
  policy: Policy
  outcome: 'approved' | 'approved-with-changes' | 'rejected' | 'noted' | 'unanswered'
  comment?: string               // 用户在卡片中写的意见
  fileDiff?: string              // "修改后通过"时审核文件的变化
  askedAt: string
  answeredAt?: string            // 与 askedAt 之差 = 人工审核耗时
}

export async function runCheckpoint(ctx: Context, agent: Agent, input: CheckpointInput): Promise<HumanReview>
```

`Task` 新增字段：`humanReviews: HumanReview[]`。

### 6.3 依赖的 DSH API

| API | 状态 | 用途 |
|---|---|---|
| `ctx.userQuestions.ask({ agent, questions: [{ id, question, detail?, header?, options?: [{ label, description? }], multiSelect?, intent?: { kind: 'plan-review', approve } }] })` | 【已核对】`dsh-user-questions/lib/index.js` L35–46、L306–320；`typert.host.js` L212 | 审核卡 |
| 只有存活的主 agent 可以发起；子 agent 调用会失败 | 【已核对】同上 README | 审核点只在主会话工具中触发；异源审查分身的结果由主会话工具转交 CP4 |
| `present` 文件卡片 | 【已核对】dsh-tool-present README | 审核文件、报告 |
| 每轮改动文件卡片与 diff review tab | 【已核对】dsh-client-ui-deliverables README | 代码 diff |
| `ctx.sidebarRightTabs.register(...)` | 【已核对接口存在】dsh-client-ui-sidebar-right README | P2 常驻看板 |

**编码第一步需要确认**：插件工具内部能否直接调用 `present` 的能力，还是只能让模型调用 `present` 工具。若只能由模型调用，则在工具结果中写明"请用 present 展示以下文件"。审核卡本身不受影响。

## 8. 对参赛材料的影响

- **展示层面**：审核卡在右侧边栏展开，是视频中最直观的"人机协作"画面；看板 HTML 可以作为封面截图。
- **新增真数据**（全部来自 `humanReviews`）：

| 指标 | 含义 |
|---|---|
| 每个任务的人工审核次数与总耗时 | 人投入了多少注意力 |
| 契约被人修改的比例 | 人在"定义完成"环节提供了多少价值 |
| CP5 驳回率 | 通过代码底线后，仍被人判为不合格的比例（衡量底线之外的质量缺口） |
| CP4 中被人标为"误报 / 接受风险"的 finding 比例 | 异源审查的噪声水平 |

> 路演说法："AiDO 在 59 个地方问你；RefactorKit 只在 6 个关键节点请你签字，而且每次都告诉你签的是什么。"（59 为关键词粗略计数，见 03 文档。）
