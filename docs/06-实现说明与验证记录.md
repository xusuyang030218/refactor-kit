## 2. 与设计的差异（实现时的决定）

| 设计 | 实现 | 原因 |
|---|---|---|
| TypeScript + 构建 | 纯 ESM JavaScript（JSDoc 注释），无构建步骤 | DSH 官方说明 Host-only bundle 无需构建；规避 tsdown 在 Windows 上的已知问题与"本地包未构建导致加载器崩溃" |
| `rk_next`（guided 档建议） | 并入 `rk_status` 的"下一步"与 `rk_task_open` 的档位建议 | 少一个工具，减少模型注意力占用 |
| `rk_skill`（技能工坊） | 推迟到 P2 | 比赛优先级 |
| 缺口按端点路径匹配 | **四种依据**：mapping / name / alias / path，逐条标注 | DTS 实测：新系统是 REST 重设计，纯路径匹配只得 0.1%（1/1187），明显失真。按类名对应后为 15.6%（估算），对应关系交 CP1 人工核对 |
| 风险 L0 包含".vue 只改文本" | `.vue` 一律至少 L1 | 无法可靠区分只改模板文本与改逻辑，宁严勿松 |
| 新增 `project.stateDir` | 账本可放到目标仓库之外 | 演示时不在被重构的仓库里留文件 |
| 新增 `truth.mapping / aliases` | 类名对应关系可配置、可在 CP1 审核文件中编辑 | 同上 |

### 3.3 在真实 DSH 中加载（隔离环境，不影响当前会话）

做法：`DSH_HOME` 指向临时目录 → `dsh --profile rktest --from-default-profile headless` 建立隔离 profile → `dsh plugin --profile rktest add "dsh-plugin-refactorkit@link:<本仓库>"` → 另装一个只在该隔离 profile 中存在的探针插件，在激活后读取注册结果并真实调用 `rk_status`。

| 检查 | 结果 |
|---|---|
| `dsh plugin add` | 成功；`dsh.bundle` 被识别，加入 bundles |
| `--dump-config` | 组合配置中出现 `id: refactorkit` 行 |
| headless 启动 | 插件加载无错误；进程停在 `MISSING_CREDENTIAL`（隔离环境没有模型密钥，符合预期） |
| 已注册 `rk_*` 工具 | **13 / 13** |
| 已注册技能 | **14 / 14** |
| 入口技能 `/refactorkit` 正文加载 | ✅ |
| 在真实 DSH 中执行 `rk_status` | ✅ 读取 DTS 项目：state=ready，缺口 110，端点覆盖率（估算）15.6% |

**这一步发现并修复了一个真实缺陷**：运行时技能缺少 `source` 字段。DSH 注册时不校验该字段，但加载正文时会校验，因此伪造上下文的测试无法发现。修复后测试中的伪造服务也加入了同样的校验。

## 4. 已知限制

| 项 | 说明 |
|---|---|
| 未安装到你正在使用的 DSH profile | 安装会修改 `desktop` profile 并通常需要重启 DSH（会中断当前会话），需要你确认后执行：`pwsh scripts/install.ps1` |
| 审核卡的界面效果未目测 | 审核卡走的是 DSH 计划模式同一套 `plan-review` 机制（已核对源码），但隔离环境没有 Web 界面，未实际截图 |
| 子智能体与真实模型未端到端跑 | `rk_delegate` / `rk_review` 的调用参数已按 DSH 源码核对并用伪造服务测试；真实模型调用需要在安装后验证 |
| 缺口匹配是估算 | name / alias / mapping 依据下的覆盖率按端点数估算，需在 CP1 人工核对 |
| 写类工具识别 | 守卫按工具名与参数特征识别写操作；DSH 新增的写类工具若命名不同，可能漏识别（DSH 自身的沙箱仍然生效） |
| 页面级缺口 | 目前只对照后端控制器；前端页面对照未实现 |
