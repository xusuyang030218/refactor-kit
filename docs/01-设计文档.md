## 0. 一页结论

| 问题 | 回答 |
|---|---|
| 一句话 | **放开过程，守住结果。** 模型自己决定用哪个技能、要不要分身、分身用什么视角和什么模型；插件只用代码守住几条不可绕过的底线（证据、异源审查、真相仲裁、写入范围） |
| 为什么 | AiDO 的分身边界很硬：岗位固定、流程固定、工具范围固定。弱模型需要这种护栏；强模型被它拖累，要在分身之间来回搬上下文，一个人能连贯做完的事被拆成 7 段【已确认】 |
| 怎么做 | **技能是按需加载的知识卡，分身是随用随建的临时视角**，是否使用由模型判断；"完成"由代码检查，不由模型宣布 |
| 检查多严 | 按**改动风险**分 L0 / L1 / L2，由 diff 事实计算：改文案只需构建证据，动接口、迁移脚本、鉴权才要求异源审查（吸收自 AiDO 的分级思路） |
| 人审什么 | **人审结果，不审过程**：6 个审核点（缺口清单、任务契约、关键决策、审查结果、交付验收、阻塞上报），以 DSH 原生审核卡 + 可编辑的审核文件 + diff 卡片 + 进度看板展示；按预设与风险决定是否阻塞等待（7.7 节、[04 文档](./04-审核与展示设计.md)） |
| 照顾弱模型 | **自主度档位**：`free`（强模型，只守底线）/ `assisted`（给建议，不强制）/ `guided`（逐步引导，接近 AiDO）。按模型配置，换模型自动切换档位 |
| 可设计性 | 技能、视角、底线阈值、档位、模型槽全部是文本或配置；新增技能一句话生成；插件根据使用日志**建议**新增或淘汰技能，由人确认 |
| 可复用 | 换项目只改一份 `refactorkit.yaml`；核心逻辑同时提供 CLI，没有 DSH 的环境和 CI 也能跑盘点、门禁、仲裁 |

## 1. 背景与需求

### 1.1 背景

案例项目 DTS 是一个 198.9 万行的企业 BI 平台，从 Spring Boot 1.5 / Vue 2 重构到 Spring Boot 3 / Vue 3。重构过程中使用 Trae CN 中的 AiDO 平台，组织了 7 个固定分身（技术设计、需求、原型、前端、后端、E2E 测试、代码分析），共 278 次会话。

暴露出的问题：

| 问题 | 证据 |
|---|---|
| AI 自报完成不可信 | 历史记录：自报 100%，量化复查实际 16%；2026-10-08 实测：自报 100%，加权实测 46.9%（`D:\DTS\DTS-rebuild\packages\support\dsh-migration-pilot\data\truth-report.json`） |
| 固定分身拖累强模型 | 分身之间靠文档接力，约 20% 会话低效（原汇报数据）；强模型本可以连续完成"读旧代码 → 改新代码 → 写测试" |
| 绑死平台模型 | 不能按任务换模型，也不能让另一家模型交叉审查 |
| 经验难复用 | 7 份大提示词混合了方法和项目事实，换项目只能整份复制再改 |

### 1.2 需求规格

| 维度 | 内容 | 状态 |
|---|---|---|
| 目标 | DSH 插件，辅助完成重构，也能推广给其他人、其他老系统 | 【已确认】 |
| 多模型 | DSH 调用不同模型，用户可配置 | 【已确认】 |
| 自主 | 模型自己决定用什么分身、什么技能；不要 AiDO 式硬边界 | 【已确认】 |
| 可修改 | 不改代码即可新增或修改技能、视角、模型、档位、门禁 | 【已确认】 |
| 成功标准 | ① 在 DTS 上用本插件完成至少 2 个真实缺口，全程留证据；② 另一个仓库只改配置就能跑通 `rk_survey`；③ 新增一个技能 ≤10 分钟；④ 底线在任何档位下都不能被绕过 | 【默认假设】 |
| 边界 | 不做无人值守全自动迁移；不新写模型适配器（复用 DSH 已配置的 Provider）；不默认执行有副作用命令 | 【默认假设】 |
| 技术约束 | DSH = Cordis 插件体系，Node.js ESM + TypeScript；模型经 `ctx.llm` / `ctx.subagents`；工具经 `ctx.tools.register` | 【已核对】 |

## 2. 设计转向：去掉什么，保留什么

| AiDO 的做法 | RefactorKit v3 | 理由 |
|---|---|---|
| 7 个固定分身，各管一段 | **不设固定分身**。提供 5 张"视角卡"（≤20 行），模型需要时用来创建临时子 Agent，也可以完全不用 | 强模型在一个上下文中连贯工作更快，也更少丢信息 |
| 分身之间靠文档接力 | 默认单会话连续工作；只有在需要**隔离上下文**或**独立第二意见**时才分身 | 分身的真实价值只有两个：省上下文、换视角 |
| 固定流程 | **不设强制流程**。`guided` 档位提供一条推荐路径，作为建议 | 每个缺口复杂度不同 |
| 分身工具范围硬隔离 | 默认全工具；只在底线处硬拦 | 约束"不能出现的结果"，而不是"能用的手段" |
| 分身绑定平台模型 | 模型槽 + 子 Agent 可以按任务指定模型 | 多模型、异源审查 |
| 靠人提醒做量化复查 | **代码强制**：关闭任务时检查证据、审查和仲裁 | 两次虚报说明这一条不能交给模型自觉 |
| 按任务复杂度分级，复杂任务走更重的流程（No / Lite / Full-SDD） | **按改动风险分级，风险高则终点检查更严**；过程仍由模型决定。风险由 diff 事实计算（7.1 节） | 保留 AiDO 分级的初衷，但把"流程变重"换成"检查变严"，且不能靠自述降级 |

> AiDO 自己也已意识到交接成本：其默认的 Lite-SDD 档位改由全栈分身"一个上下文做齐，避免跨分身交接损耗"。10 份提示词的逐项分析与吸收清单见 [03 文档](./03-AiDO分身分析与吸收.md)。

## 3. 设计原则

1. **约束结果，不约束过程**：插件只定义"什么算完成"（任务契约 + 底线），不定义"怎么完成"。
2. **技能是知识，不是流程**：技能回答"这类问题有哪些坑、标准是什么"，不规定"第 1 步、第 2 步"。模型凭技能描述自己决定是否加载。
3. **分身是视角，不是岗位**：分身 = 一段视角提示 + 一个模型 + 可选工具过滤，用完即弃。只有"独立第二意见"（异源审查）是强制的。
4. **底线写在代码里**：凡是"模型忘了也必须成立"的规则，都由工具层守卫和校验执行，不写进提示词祈祷模型遵守。
5. **可以进化，但由人拍板**：插件记录模型的选择和结果，据此建议新增、修改或淘汰技能，所有改动由人确认。
6. **核心与宿主分离**：确定性逻辑（扫描、门禁、证据、仲裁、账本）是不依赖 DSH 的纯函数，DSH 工具和 CLI 共用同一份实现。

```text
┌──────────────────────────── DSH 主会话（用户选的模型）────────────────────────────┐

│       ▼                    ▼                        ▼                             │
│ ┌───────────┐     ┌────────────────┐     ┌────────────────────────┐               │
│ │ 技能目录   │     │ 视角卡 lenses   │     │ rk_* 原子能力（工具）   │               │
│ │ 按需加载   │     │ 分身时作 persona │     │ 盘点/缺口/门禁/证据/仲裁 │               │

│  ① 证据 ② 异源审查 ③ 仲裁非虚报 ④ 写入范围 ⑤ 命令白名单 ⑥ 账本只经工具写 ⑦ 预算   │
│        ctx.tools.guard  +  rk_task_close 内部校验  +  DSH 文件沙箱                  │

                    │ 同一份 core/*
              bin/rk.mjs（CLI：survey / gate / truth，供 CI 或无 DSH 环境）
```

### 4.1 任务生命周期

这是唯一的固定结构，因为它定义的是"结果"，不是"过程"：

```text
OPEN ──(模型自主工作，任意路径)──► 申请关闭 ──► 底线检查 ──全部满足──► DONE
  ▲                                            │
  └──────── 不满足：返回缺哪几条 ◄──────────────┘      超出预算 ──► BLOCKED（交给人）
```

不满足时，插件**明确告诉模型缺什么**（例如"缺少 unit 门禁证据""审查者与实施者同源"），由模型自己决定怎么补。

## 5. 自主决策机制

### 5.1 选技能：依靠 DSH 原生技能目录

- DSH 会把每个技能的 `name`、`description`、`whenToUse` 放进模型可见的目录，正文按需加载【已核对 dsh-skill】。"模型自己选技能"是 DSH 原生能力，插件不另写选择器。
- 插件要做的是**把描述写好**：`description` 写清解决什么问题；`whenToUse` 写清出现什么信号时有用，并写出反向条件（如"如果只是改字段名，不需要本技能"）。
- 内置技能通过 `ctx.skills.register({ name, description, whenToUse, content })` 注册【已核对】。项目自定义技能放在 `<目标仓库>/.agents/skills/<name>/SKILL.md`，同名时项目技能优先于运行时技能【已核对】，因此用户可以覆盖任何内置技能。

### 5.2 分身：模型调用 `rk_delegate` 时才发生

```ts
rk_delegate({
  lens: 'skeptic',             // 视角卡名；或传 lensText 临时写一段
  slot: 'reviewer',            // 模型槽；或直接传 provider + model
  task: '审查 T-07 的 diff 是否兑现契约，只输出问题清单',
  tools: 'read-only',          // 'all' | 'read-only' | 工具名数组
  why: '需要独立第二意见',      // 必填，一句话理由，写入决策日志
  outputSchema: 'finding-list' // 可选：要求结构化输出
})
```

插件内部调用【已核对 dsh-subagent】：

```ts
ctx.subagents.start('spawn', {
  label: `rk:${lens}`,
  prompt: task,
  parent,                                    // 当前 agent（来自工具执行上下文）
  persona: lensText,                         // 注入为子 Agent 系统提示词的 persona 段
  agentOptions: { provider, model, reasoningEffort },
  toolFilter,                                // read-only → 拒绝写类工具
  outputSchema,                              // 对象型 JSON Schema
  signal,
})
```

**何时值得分身**（写在内置技能 `rk-playbook` 中，作为判断依据，不是规则）：

| 信号 | 建议 |
|---|---|
| 需要独立第二意见（审查、验收） | 分身，并换一家模型（底线 ② 本来就要求） |
| 要读大量旧代码，但只需要结论 | 分身做"阅读摘要"，避免撑爆主上下文 |
| 几个互不依赖的子任务 | 并行分身 |
| 任务连贯、上下文已经在手 | **不要分身**，直接做 |

### 5.3 决策日志

每次 `rk_delegate`、每次技能加载（通过 `tools/post-execute` 观察 `skill` 工具调用）、每次 `rk_task_close` 的结果，都写入 `.refactorkit/journal.jsonl`，用于：
1. 复盘：模型为什么这样做；
2. 进化：统计技能命中率与贡献（第 10 节）；
3. 评估：不同档位、不同模型的对比数据。

## 6. 自主度档位

| 档位 | 适用 | 插件行为 | 底线 |
|---|---|---|---|
| `free` | 强模型 | 只提供工具与技能目录；不推荐步骤；`rk_next` 不可见 | 全部生效 |
| `assisted` | 中等模型 | `rk_task_open` 返回时附带"建议路径"和"建议技能"，可以不采纳 | 全部生效 |
| `guided` | 弱模型或新手演示 | `rk_next` 逐步给出下一步；当前步未完成时不给下一步（软约束） | 全部生效 |

档位按当前 agent 的 `provider/model` 匹配，主会话换模型时自动切换；匹配不到时用 `default`。用户可以用命令临时覆盖，覆盖会写入 journal。

**要点**：三个档位的底线完全相同，区别只在"给多少建议"。因此不同档位之间的结果可以直接对比。

## 7. 底线（不可绕过）

| # | 底线 | 执行方式 | 失败时返回给模型的信息 |
|---|---|---|---|
| ① | 契约中每条断言都有 pass 证据 | `rk_task_close` 内部校验 | `缺少证据: [A2 单测, A4 冒烟]` |
| ② | （L2）至少一次异源审查结论为 pass，且审查者 provider ≠ 实施者 provider | `rk_task_close` 校验审查记录；provider 取自子 Agent 实际使用的路由，不取模型自报 | `风险 L2（命中：迁移脚本）。审查与实施同源(anthropic)，请用其他来源复审` |
| ③ | （L1 及以上）真相仲裁不是 `FALSE_CLAIM` | `rk_task_close` 内部调用仲裁 | `自报 100%，实测 58%，差距超过 15 个百分点` |
| ④ | 只写 `writeScope`；老仓库只读 | DSH 文件沙箱 + `ctx.tools.guard` 检查写类工具目标路径 | 沙箱或守卫的拒绝理由 |
| ⑤ | 门禁命令只能命中 `commandAllowlist`；`sideEffect` 命令需审批 | `rk_gate` 内部校验 + `tools/pre-execute` 返回 ask | `命令不在白名单` |
| ⑥ | 账本只能经 rk 工具修改 | `ctx.tools.guard`：写类文件工具指向 `.refactorkit/` 时拒绝 | `.refactorkit 由 RefactorKit 管理，请使用 rk_* 工具` |
| ⑦ | 单任务 token 与分身次数上限 | `rk_delegate` / `rk_task_close` 累计用量，超限后转为 `BLOCKED` | `已超预算，交由人工决策` |

`ctx.tools.guard` 的语义【已核对】：同步函数，返回字符串即拒绝；任何守卫的拒绝都不能被其他守卫或监听器改为放行。

**实施者如何确定**：任务打开后，在主会话和非审查类子 Agent 中，凡是调用写类工具的 agent，都记为实施者，并记录其 provider。依据是工具执行上下文中的 `exec.agent`，不是模型声明。

### 7.1 风险分级：底线强度随改动风险变化（吸收自 AiDO 分级）

不是所有改动都需要异源审查：改一个文案也要换家模型审，就又成了累赘。所以底线分三级，**风险等级在 `rk_task_close` 时根据 `git diff baseRef` 的事实计算**，取命中的最高级，不接受模型自述：

| 等级 | 判定信号（任一命中即升级） | 需要满足的底线 |
|---|---|---|
| **L0 微小** | 只改 ≤2 个文件；只涉及文案、样式、注释、常量；不含 L1/L2 信号 | ① 证据（至少一条构建或编译类断言通过）、④⑤⑥⑦ |
| **L1 常规** | 改动 >2 个文件，或涉及业务逻辑文件（Service、组件脚本） | L0 + ③ 真相仲裁 |
| **L2 高风险** | 新增或修改 Controller / 路由 / 接口签名；迁移脚本（`db/migration/**`、`*.sql`）；鉴权或权限相关路径（`**/auth/**`、`**/security/**`、含 `StpUtil`、`@SaCheck*` 的改动）；依赖清单（`pom.xml`、`package.json`）；跨 ≥2 个顶层模块 | L1 + ② 异源审查 |

判定规则写在 `refactorkit.yaml` 的 `risk` 段，可按项目调整（见 11.3）。判定结果和命中信号写入任务记录与报告，便于复核。

### 7.2 不可逆操作清单（吸收自 AiDO "不可逆先征询"）

以下操作无论在哪个档位，都通过 `tools/pre-execute` 返回 `ask`，交给 DSH 原生审批：

| 类别 | 识别方式 |
|---|---|
| 数据库写入 | 门禁或终端命令中含 `psql`/`mysql` 且带 `INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE`；执行 `flyway migrate` |
| 改写 git 历史或推送 | `git push`、`git reset --hard`、`git rebase`、`git commit --amend`、`git checkout -- .` |
| 依赖变更 | `npm/pnpm install|add|remove`、`mvn install` 写入本地仓库、修改锁文件 |
| 有副作用的门禁 | `gates.*.sideEffect: true`（如会写业务数据的冒烟脚本） |

识别只针对 `rk_gate` 和宿主终端类工具（`pwsh` / `bash`）的命令文本；规则列表可在配置中扩展。识别不到不等于安全：DSH 原有的沙箱和审批策略仍然生效。

### 7.3 证据双状态（吸收自 AiDO "execution_status / assessment"）

每条证据同时记录两个状态：

| 字段 | 取值 | 含义 |
|---|---|---|
| `exec` | `ran` / `env-failed` / `timeout` / `denied` | 命令本身是否成功运行 |
| `verdict` | `pass` / `fail` / `pending` | 项目是否满足断言；`exec ≠ ran` 时只能是 `pending` |

这样"沙箱拦截、缺 JDK、`spawn EPERM`"这类环境问题（EvidencePilot 实测遇到过）不会被误记为项目失败，也不会被当作通过。

### 7.4 失败上限（吸收自 AiDO "最多 3 轮"）

- 同一断言连续 `fail` 3 次 → 任务转为 `BLOCKED`，附上 3 次的证据，交给人决定。
- `rk_review` 连续 `reject` 3 次 → 同上。
- `rk_task_close` 被拒 5 次 → 同上，避免模型在关闭和补证据之间来回循环。

### 7.5 越界自检（吸收自 AiDO "收尾自检"，改为自动生成）

`rk_task_close` 的返回结果和报告中自动附上：
- 本任务期间被修改、但不在 `writeScope` 内的文件（正常情况下守卫已拦截，这里作为复核）；
- 本任务期间执行过的不可逆类命令及审批结果；
- 任务打开期间、但不属于任何任务的文件改动（"无任务改动"）。

数据全部来自 journal，不依赖模型自述。

### 7.7 人工审核点（详见 [04-审核与展示设计.md](./04-审核与展示设计.md)）

代码底线只能证明"满足契约"；"契约本身对不对、决策合不合适、交付是否真的可用"需要人判断。插件在 6 个节点生成审核材料：

| 审核点 | 触发 | standard 预设 |
|---|---|---|
| CP1 缺口清单 | 首次盘点；新增 / 拆分 / **裁撤**缺口 | block（裁撤始终 block） |
| CP2 任务契约 | `rk_task_open` | 预估 L2 block，其余 notify |
| CP3 关键决策 | `rk_decide`；任务中首次出现 L2 信号 | block / notify |
| CP4 审查结果 | `rk_review` 完成 | notify（blocker 被标"不修"时 block） |
| CP5 交付验收 | `rk_task_close` 底线全部通过之后 | 实际 L2 block，L1 notify，L0 off |
| CP6 阻塞上报 | 任务转为 `BLOCKED` | 始终 block |

展示用 DSH 原生能力，MVP 不写前端：`ctx.userQuestions.ask()` 带 `intent: plan-review` 的审核卡（与计划模式同一审阅界面）+ `.refactorkit/review/` 下可直接编辑的 Markdown 审核文件 + DSH 每轮 diff 卡片 + `report.html` 看板。`block` 审核点无应答时保持未通过，不默认放行；CP5 为 `block` 时，人工通过是 `DONE` 的必要条件。

### 7.8 无任务改动提示（吸收自 AiDO "直修计数"，软约束）

模型可以不开任务直接改小东西。插件通过 `tools/post-execute` 统计没有打开任务时的写类工具调用：累计改动 ≥5 个文件，或触及 ≥2 个顶层模块时，在下一次工具结果后附一句提示："这些改动未纳入任务，建议用 `rk_task_open` 登记，以便验收"。只提示，不拦截。

## 8. 原子能力（插件工具）

| 工具 | 作用 | 关键参数 | 副作用 |
|---|---|---|---|
| `rk_survey` | 盘点新旧仓库：文件计数、Spring 端点 / Vue 路由抽取、占位实现扫描 | `scope?`, `refresh?` | 写 `facts.json` |

| `rk_task_open` | 为缺口打开任务，**模型自己写契约**；断言必须可验证（命令 + 期望） | `gapIds`, `contract: Assertion[]`, `budget?`, `fromOpenspec?`（P2：从 OpenSpec change 的 tasks.md 导入断言草稿，见 03 文档第 6 节） | 写账本 |

| `rk_review` | 快捷异源审查：自动选与实施者不同源的 reviewer 候选，用 `skeptic` 视角审查 diff 与契约 | `taskId` | 写审查记录 |
| `rk_gate` | 执行命名门禁或契约断言，保存原始证据 | `taskId`, `assertionIds? / gateIds?` | 依命令而定 |
| `rk_truth` | 自报与实测仲裁 | `taskId?`, `selfReported` | 无 |
| `rk_task_close` | 申请关闭任务，执行底线检查 | `taskId`, `selfReported`, `summary` | 写账本 |
| `rk_next` | 仅 `assisted` / `guided` 档位可见：建议下一步 | `taskId` | 无 |
| `rk_note` | 写入项目记忆（坑点、决策、事实），会话开始时注入摘要 | `kind: pitfall/decision/fact`, `text` | 写 `memory.md` |
| `rk_skill` | 技能工坊：起草、lint、统计、给出进化建议 | `op: draft/lint/stats/suggest` | 草稿写入 `.agents/skills/_drafts/` |
| `rk_decide` | 模型主动请人拍板关键决策（CP3） | `taskId`, `question`, `options[≥2]: { label, impact, cost }`, `recommend`, `why` | 写审核文件；`block` 时等待 |
| `rk_report` | 生成进度看板 `report.html` 并以文件卡片展示 | `open?` | 写 `.refactorkit/report.html` |

触发审核点的工具：`rk_gaps`（CP1）、`rk_task_open`（CP2）、`rk_review`（CP4）、`rk_task_close`（CP5 / CP6）。审核点只能由主会话的工具触发（DSH 限制：子 agent 不能发起人机交互）。

`rk_next` 通过 `ctx.tools.restrict` 按 agent 隐藏【已核对】。`free` 档位看不到它，不占用模型注意力。

### 9.3 视角卡（分身时用作 persona）

存放于插件 `lenses/<name>.md`，项目可在 `<目标仓库>/.agents/refactorkit/lenses/` 覆盖。每张 ≤20 行。

| 视角 | 一句话 | 典型搭配 |
|---|---|---|
| `skeptic` | 默认不相信"完成了"；只看契约、diff 和证据；逐条输出问题 | 异源 reviewer、只读工具 |
| `archaeologist` | 在旧代码中找出功能的真实边界和隐藏逻辑，只输出结论和出处 | fast 槽、只读工具 |
| `architect` | 关注模块边界、数据模型、可演进性；输出决策与取舍 | strong 槽 |
| `tester` | 从用户路径和异常路径补测试；断言必须可执行 | 当前会话模型 |
| `user-proxy` | 站在业务用户角度检查页面是否"能用"，不只是"能跑" | 多模态模型 |

模型也可以不用视角卡，直接传 `lensText`。

**与 AiDO 分身的对应关系**：视角卡只保留 AiDO 分身中"看问题的角度"，去掉身份红线、固定流程和工具限制。

| 视角卡 | 对应 AiDO 分身 | 保留 | 去掉 |
|---|---|---|---|
| `skeptic` | 代码分析 | 只读审查、按风险读文件、四维度 | 固定 6 步流水线、范围确认询问、只能产报告的身份 |
| `archaeologist` | 需求数字、技术设计（读现状部分） | 从真实代码提炼现状，证据优先 | 必须先产 proposal / specs |
| `architect` | 技术设计 | 设计决策可追溯、架构风险视角 | "绝不编码"、Step 0–3 门禁 |
| `tester` | E2E 测试 | 测试类型选择、真实执行、交互五环 | 用例必须先经用户确认 |
| `user-proxy` | 原型设计 | 需求与交互双向对齐、状态覆盖 | Fast / Standard / Full 仪式 |

前端、后端、全栈开发分身不设视角卡：编码由主会话直接完成，这正是 AiDO 自身 Lite-SDD 档位的做法。

### 9.4 技能文件格式

遵循 DSH `dsh-skill-filesystem` 格式【已核对】：frontmatter 必填 `name`、`description`，可选 `whenToUse`、`metadata`；修改后无需重启。RefactorKit 的扩展信息只放在 `metadata.refactorkit` 下，其他兼容 `SKILL.md` 的工具会忽略它。

```markdown
---
name: rk-mybatis-flyway
description: MyBatis-Plus 与 Flyway 迁移脚本的规范和常见事故，避免启动失败和数据不一致。
whenToUse: 需要新增或修改数据库表、写 Flyway 脚本、或启动时报 Flyway 校验错误时。只改 Java 业务逻辑时不需要。
metadata:
  refactorkit:
    kind: knowledge          # knowledge | project
    relatedTools: [rk_gate]
    relatedInvariants: [evidence]
---

# 要点
- 已发布的 V 脚本永远不改；需要变更时新建版本。
- 版本号一旦用过就不能复用，即使原脚本从未入库。
...

# 常见失败信号
- `Validate failed: Migration checksum mismatch` → 有人改了已发布脚本。
...
```

### 12.4 核心数据结构

```ts
interface ModelRef { provider: string; model: string }

interface Task {
  id: string                          // 'T-07'
  gapIds: string[]
  contract: Assertion[]
  status: 'OPEN' | 'DONE' | 'BLOCKED'
  baseRef: string                     // 打开时 git HEAD
  implementers: Array<ModelRef & { agentId: string }>   // 由守卫观察写类工具的 exec.agent 得出
  reviews: Review[]
  evidence: Record<string, string[]>  // assertionId → evidenceIds
  truth?: { selfReported: number; measured: number; gap: number; verdict: TruthVerdict }
  usage: { tokens: number; delegations: number }
  risk?: { level: 'L0' | 'L1' | 'L2'; signals: string[] }   // 关闭时按 diff 计算，如 ['path:db/migration/V37__x.sql']
  failStreak: Record<string, number>                         // assertionId 或 'review' → 连续失败次数
  closeAttempts: Array<{ at: string; risk: 'L0' | 'L1' | 'L2'; missing: string[] }>
  outOfScope?: { files: string[]; irreversible: Array<{ command: string; approved: boolean }> }  // 7.5 越界自检
  humanReviews: HumanReview[]          // 7.7 人工审核记录，结构见 04 文档 6.2 节
  openedAt: string; closedAt?: string
}
type TruthVerdict = 'CONSISTENT' | 'NEEDS_REVIEW' | 'FALSE_CLAIM'

interface Assertion {
  id: string
  statement: string                   // 人可读的断言
  check: { gate?: string; command?: string; cwd?: string; expectExit?: number; expectPattern?: string }
  kind?: 'build' | 'test' | 'api' | 'ui' | 'other'   // L0 要求至少一条 build 类通过
  trace?: string                      // 可选：指向设计决策或 OpenSpec tasks.md 行，如 'openspec:export-xlsx#L12'
}

interface Review { reviewer: ModelRef & { agentId: string }; verdict: 'pass' | 'reject'; findings: Finding[]; at: string }
interface Finding { severity: 'blocker' | 'major' | 'minor'; file?: string; line?: number; message: string }

interface Evidence {
  id: string; sha256: string; path: string
  exec: 'ran' | 'env-failed' | 'timeout' | 'denied'  // 7.3：命令是否真正运行
  verdict: 'pass' | 'fail' | 'pending'               // exec ≠ 'ran' 时恒为 'pending'
  command?: string; exitCode?: number; durationMs?: number
  excerpt: string                     // 输出尾部 2KB
  collectedAt: string
}

interface JournalEntry {
  at: string; taskId?: string; agent: ModelRef & { agentId: string }
  kind: 'skill-load' | 'delegate' | 'close-ok' | 'close-denied' | 'gate' | 'note' | 'autonomy-override'
  detail: Record<string, unknown>     // delegate: { lens, slot, why, tokens }；close-denied: { missing }
}
```

### 12.6 失败处理

| 情况 | 处理 |
|---|---|
| 模型调用失败 | 依据 `ctx.llm` / 子 Agent 结果中的稳定错误码：`RATE_LIMIT`、`QUOTA` → 换下一个候选；`AUTH`、`MISSING_CREDENTIAL`、`NO_ADAPTER` → 不重试，提示去"设置 → 模型"修复 |
| 子 Agent provider 缺能力 | `UNSUPPORTED_CAPABILITY` → 去掉相应可选项（如 `outputSchema`）重试一次，仍失败则报告 |
| 门禁超时 | 证据记为 `fail(timeout)`，保留已有输出 |
| 账本并发写冲突 | `STALE_REVISION` → 重新读取后重放一次；仍冲突则报错 |
| 配置非法 | 插件加载时报错并指出字段；不注册工具，避免带病运行 |


## 14. 反例与对策

| 反例 | 对策 |
|---|---|
| 模型写一个"永远通过"的断言（如 `echo ok`） | 断言命令也必须命中白名单；`skeptic` 视角专门检查断言是否覆盖契约 |
| 模型过度分身，浪费 token | 预算底线 ⑦；journal 统计每次分身的 token 与产出是否被后续使用 |
| 模型从不加载技能，重复踩坑 | 关闭被拒时附带"相关技能提示"（按缺失项匹配 `whenToUse`），只提示不强制 |
| 两个"异源"模型背后是同一底座 | 比较 provider 与 model；报告如实列出，由人判断（已知局限） |
| 用户只有一家模型 | 异源审查降级为"同源但隔离上下文的 skeptic 分身"，报告标红"未满足异源" |
| 档位按模型名匹配不准 | 匹配不到时用 `default`；可临时覆盖并记入 journal |
| 用户把技能改坏 | DSH 技能注册表会丢弃格式错误的技能并告警；`rk_skill lint` 提供更细检查 |
| 文件数口径误导完成度 | `truth` 输出 `cautions`；`retired` 白名单；最终以缺口清单的端点级、页面级对照为准 |
| 模型把高风险改动说成"小改动"，想跳过异源审查 | 风险等级只在关闭时按实际 diff 计算，模型无法指定；命中信号写入报告 |
| 风险规则误判：改了一个 `package.json` 的 description 也被判为 L2 | 宁严勿松（与 AiDO "拿不准从高"一致）；项目可在 `risk` 段调整规则，调整本身记入 journal |
| 环境问题（缺 JDK、沙箱拦截）导致门禁跑不起来 | 证据记为 `exec: env-failed, verdict: pending`，不算项目失败，也不能用于关闭；报告单列"环境阻塞" |
| 命令绕过不可逆识别（例如写进脚本文件再执行） | 正则识别只是第一道；DSH 沙箱与审批策略仍然生效；`rk_gate` 只执行白名单命令 |
