# RefactorKit 面板设计（一个界面完成配置与审核）

> 版本：v0.2（2026-10-09）｜ 需求【已确认】："用一个界面吧，一个一个提问太麻烦了，配置也放在界面里面进行配置"

## 1. 形态

DSH 右侧栏的一个标签页 **RefactorKit**（与计划模式审阅面板同一区域）：

- 打开方式：右侧栏「+」引导页中的 RefactorKit 入口；或有待审核项时**自动打开**。
- 面板按**当前会话的工作目录**定位项目（Host 用 `ctx.sessions.get(sessionId).header.cwd` 解析），切换会话即切换项目。
- 样式只使用 DSH 主题令牌（`--dsw-alias-*`），随浅色/深色主题变化。

## 2. 五个分区

| 分区 | 内容 | 你能做什么 |
|---|---|---|
| **待审核**（有待办时默认显示） | 所有等待你决定的审核点（CP0–CP6）与待阅材料 | 看摘要；直接编辑可编辑块（契约、类名对应、裁撤清单）；通过 / 修改后通过 / 驳回 / 写意见；待阅项点「已阅」 |
| **概览** | 状态、缺口统计、任务列表、下一步建议 | 一键盘点、刷新缺口、生成看板 |
| **缺口** | 缺口表（状态、覆盖率、匹配依据、对应新类），可筛选 | 改正类名对应、裁撤 / 撤销裁撤、备注（这些都是你的直接操作，不再弹审核卡） |
| **任务** | 每个任务的契约、断言结果与证据、审查、人工审核记录 | 查看证据摘要 |
| **配置** | 未初始化时为"初始化向导"；已初始化时为配置表单 | 项目路径与写入范围、模型槽（下拉选择 DSH 已配置的模型）、门禁表、命令白名单、审核预设、自主度 | 

## 3. 审核从"提问"改为"面板集中处理"

| | 之前 | 现在 |
|---|---|---|
| 阻塞审核点 | 每个审核点弹一张问答卡 | 写入面板「待审核」，面板自动打开；工具在后台等待你在面板里的决定 |
| 编辑 | 打开审核文件改 YAML 代码块 | 面板里直接编辑（仍同步写回审核文件留档） |
| 配置 | rk_init 弹 CP0 卡 + 改文件 | 面板表单；保存即通过 CP0 |
| 无面板时 | — | 自动回退为问答卡（如 headless、未打开 Web 界面） |

"有面板"的判定：浏览器端插件每 3 秒向 Host 报到并拉取待审核项；15 秒内有报到即视为面板可用。`refactorkit.yaml` 中 `review.ui: auto | panel | card` 可强制指定（默认 auto）。

## 4. 接口（Host 同源路由，仅接受本机请求）

| 路由 | 方法 | 作用 |
|---|---|---|
| `/refactorkit/api/context?session=` | GET | 会话工作目录 → 项目根、是否已初始化、配置错误 |
| `/refactorkit/api/state?root=` | GET | 状态、缺口、任务、待审核、待阅 |
| `/refactorkit/api/pending` | GET | 全部待审核项（浏览器端轮询，兼作报到） |
| `/refactorkit/api/review` | POST | 答复审核：`{ id, outcome, selected?, comment?, edited? }` |
| `/refactorkit/api/ack` | POST | 待阅项标记已阅 |
| `/refactorkit/api/config` | GET / POST | 读取 / 保存配置（保存前用与 CLI 相同的校验器校验） |
| `/refactorkit/api/detect` | POST | 初始化向导：探测技术栈并生成草稿 |
| `/refactorkit/api/init` | POST | 初始化向导：写入 refactorkit.yaml（记为 CP0 已通过） |
| `/refactorkit/api/models` | GET | DSH 已配置的 provider 与模型（模型槽下拉） |
| `/refactorkit/api/action` | POST | `survey` / `gaps` / `retire` / `unretire` / `mapping` / `note` / `report` |

## 5. 实现

- Host：`src/plugin/broker.js`（待审核中转，内存 + 账本留痕）、`src/plugin/web.js`（路由，`ctx.inject(['webServer'])` 可选注入，headless 下自动跳过）。
- 浏览器：`client/index.js`，手写的 `window.__ModuleLoader__.load` 包装，`React.createElement` 构建，无构建步骤；`package.json` 声明 `dsh.client`。
- 注册：`ctx.sidebarRightTabs.register({ id, kind: 'refactorkit', guide })` + `ctx.slots.register({ name: 'sidebar.right.pane.tab', key: id, inject: (sessionId) => ... })`。

## 7.1 滚动穿透（v0.6 定位并修复）

用户反馈两次「往下拉会拉出会话的区域」。第一次只给 `.rk-body` 加了 `overscroll-behavior:contain`，没根治——因为**滚动链并不只从 `.rk-body` 发起**。

用无头浏览器 + CDP 实测（`Emulation.setFocusEmulationEnabled` 后 `Input.dispatchMouseEvent` 的 mouseWheel 才生效，并给所有容器挂 scroll 监听）得到结论：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| `.rk-body`（面板主体）滚到底 | 不穿透（上次的修复生效） | 不穿透 |
| `.rk`（面板根）`overscroll-behavior` | **`auto`** ← 漏洞 | `contain` |
| 面板**头部 / 标签栏**区域滚动 | 滚动链穿过 `.rk` → DSH 的 `_tabHostBody`（`overflow:auto`）→ 带动外层 | 无任何容器滚动 |
| 报告 iframe 内部滚到底 | iframe 内 `html`/`body` 的 `overscroll-behavior` 为 `auto`，跨文档链无保护 | 内层为 `contain`，外层不动 |

根因：`.rk` 是 `overflow:hidden` 的滚动容器，但没设 `overscroll-behavior`。在**头部、标签栏等不属于 `.rk-body` 的区域**滚动时，滚动链会越过 `.rk` 交给 DSH 的 tab 宿主容器，把它（乃至更外层）带动，表现为"往下拉把会话区拉出来"。

修复：`.rk` 加 `overscroll-behavior:contain`，并用一条统一规则把**所有**可能滚动的容器（`.rk-head/.rk-tabs/.rk-steps/.rk-places/.rk-body/.rk-dirs/.rk-dlg-list/.rk-md pre/.rk-pre/.rk-reportwrap/.rk-report`）都设为 `contain`；同时给看板 HTML 的 `html,body` 也加上（报告新窗口打开时同样受保护）。

## 8. v0.5 增补（2026-10-10）：顺序与"如何开始"

用户反馈：「如何开始等等没有，检查下问题，一个整个顺序的问题」。核对后确认三个真实缺陷并修复：

| 缺陷 | 原因 | 修复 |
|---|---|---|
| 阶段顺序断裂 | 阶段条只有 盘点 → 技术选型 → 实施 → 验证 → 收尾，**漏掉"生成缺口清单"**，盘点后直接跳到技术选型 | 改为 6 步：**盘点 → 缺口清单 → 技术选型(可选) → 实施 → 验证 → 收尾**；`stageList()` 统一推导，面板与测试共用同一份顺序 |
| 没有"如何开始" | 只有页面底部的 `nextSteps` 文字，用户不知道该点哪里 | 概览页**最上方**新增引导卡（`StartGuide`）：按当前状态给出**唯一**的下一步 + 可直接点的按钮（开始盘点 / 生成缺口清单 / 去审核 / 继续推进 / 去缺口页挑一个），并列出最大的三个缺口 |
| 缺口页没有开工入口 | 缺口行只有「对应」「裁撤」，没有"开始重构" | 每行新增 **「开始重构」**：复制一句可直接粘贴的指令（`请用 rk_task_open 开始重构缺口 G-x …`）到剪贴板。插件无法直接向会话注入消息，复制是当前唯一可靠的一键入口 |
| 对话侧流程缺技术选型 | 入口技能的状态表没有技术选型环节，模型不知道有面板咨询待处理 | `skills/refactorkit/SKILL.md` 增加**完整顺序图**、ready 状态**主动给建议**（挑 3-5 个缺口并给建议顺序与理由）、**技术选型处理**（`rk_tech_advise`）三节 |

同时把 `computeStatus` 的 ready 分支从"按用户意图选择缺口"改为可执行指引（先列 3-5 个最值得先做的缺口并给理由；技术方向未定先 `rk_tech_advise`），使模型的下一步与面板引导卡保持一致。
