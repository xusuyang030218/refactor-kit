## 2. AiDO 的整体结构

```text
智能调度（总指挥）
  ├─ 分级：No-SDD（直接改）/ Lite-SDD（默认，全栈一个上下文）/ Full-SDD（七分身链路）
  └─ Full-SDD：需求 → 原型 → 技术设计 → 前端 / 后端 → E2E 测试 → 代码分析
        每个分身：读提示词 → 加载执行手册 → 进入首个 Step → 打印身份自检 → 产出 → /compact
制品主线（OpenSpec）：proposal → specs → design + contracts → tasks → apply → verify → archive
外部依赖：mcp_skillshub（技能下载）、openspec / aispec CLI、gate.py / triage.py、GitNexus、API Registry
```

## 3. 值得保留的设计（RefactorKit 吸收方式）

| # | AiDO 中的做法 | 出处 | RefactorKit 吸收为 | 形态 |
|---|---|---|---|---|
| 1 | **证据优先**：接口、枚举、字段、serviceCode 必须有工具证据，禁止凭推导编造 | 后端、全栈、技术设计 | 知识技能 `rk-evidence-first` | 技能 |
| 2 | **诚实勾选**：部分完成、推迟、跑不了的任务不勾；不伪造完成状态 | 后端、全栈 | 底线 ①：断言没有 pass 证据就不能关闭 | 代码 |
| 3 | **交付即验证**：执行验收命令并记录退出码 | 全栈、E2E | `rk_gate` 证据（命令 / 退出码 / 耗时 / sha256） | 代码 |
| 4 | **不可逆先征询**：数据库写、迁移脚本、改写 git 历史、写依赖锁文件前先问 | 全栈、后端、CUC | 底线 ⑤ 扩展为"不可逆操作清单"，命中时触发 DSH 审批 | 代码 |
| 5 | **先取证再判定"简单"**：用 triage 脚本按改动路径判断能否直改 | 全栈 | **风险等级由 diff 事实计算**（第 4 节），不由模型自述 | 代码 |
| 6 | **分级**：No / Lite / Full-SDD；Fast / Standard / Full 复杂度指纹；S / N 轻重分级 | 调度、原型、前端 | 风险分级决定底线强度：小改动不必走异源审查 | 代码 |
| 7 | **执行状态与评估结论分开**：`execution_status` 与 `frontend_assessment` 双状态 | 前端 | 证据分 `exec`（环境是否跑起来）与 `verdict`（项目是否通过）；环境失败不算项目失败 | 代码 |
| 8 | **重试上限 3 轮**，不收敛就停手上报 | 前端、代码分析 | 同一断言连续失败 3 次 → 任务转 `BLOCKED`，交给人 | 代码 |
| 9 | **直修计数**：第 3 次直修或触及 ≥2 个模块时，提问是否转流程 | 全栈 | 无任务改动计数：超阈值时**提示**打开任务（软约束） | 代码（提示） |
| 10 | **收尾自检**：如实声明是否改了报告以外的文件、是否执行过写命令 | 代码分析 | `rk_task_close` 根据 journal 自动生成越界清单，不靠模型自述 | 代码 |
| 11 | **Trace 双向可追溯**：每个实现任务指向设计决策 D-* | 技术设计 | 契约断言可选 `trace` 字段；兼容 OpenSpec 时从 tasks.md 导入 | 数据结构 |
| 12 | **范围蔓延上报**：超出 spec 的工作不默默吸收 | 全栈 | `writeScope` 外写入被守卫拒绝；新增工作通过 `rk_gaps add` 显式登记 | 代码 |
| 13 | **只读审查**：分析者不改码、不跑写命令 | 代码分析 | `skeptic` 视角分身默认 `tools: read-only`（DSH `toolFilter`） | 视角卡 |
| 14 | **按风险读文件**：高风险（配置/入口/API）全读，低风险跳过或 grep | 代码分析 | 写入 `skeptic` 视角卡与 `rk-review-dimensions` 技能 | 技能 |
| 15 | **审查维度**：质量 / 性能 / 安全 / 架构 | 代码分析 | 知识技能 `rk-review-dimensions` | 技能 |
| 16 | **架构风险评估**：12 维度 + 风险登记册 + Go / No-Go | 技术设计 | 知识技能 `rk-arch-risk`（可选） | 技能 |
| 17 | **交互五环**：触发 → 即时反馈 → 结果呈现 → 异常路径 → 边界 | 前端 | 写入 `rk-vue2-to-vue3` 与 `tester` 视角卡 | 技能 |
| 18 | **测试类型路由**：UI / 接口 / 单元；用例必须全量真实执行；覆盖率 <80% 标注 | E2E | 知识技能 `rk-test-strategy` | 技能 |
| 19 | **高危 SQL**：标注版本与风险等级，附回滚方案 | CUC | 知识技能 `rk-db-safety` | 技能 |
| 20 | **断点续跑**：按 change 隔离的状态文件 | 技术设计 | `.refactorkit/tasks.json` 按任务隔离 | 数据结构 |
| 21 | **一个上下文做齐两端**，避免跨分身交接损耗 | 调度（Lite-SDD 默认）、全栈 | **v3 的默认工作方式** | 原则 |

## 4. 在强模型下成为负担的设计（RefactorKit 去除方式）

| AiDO 中的做法 | 负担 | RefactorKit |
|---|---|---|
| 每个分身开头都有技能下载样板（48h 节流、`mcp_skillshub`、询问是否更新），9/10 份重复 | 每次会话先做与任务无关的事；同一规则改 9 处 | 删除。DSH 原生发现 `.agents/skills/`，改了就生效 |
| 身份红线：需求分身"无论如何不写代码"，技术设计"绝不编码"，前端"只做前端" | 一个连贯的小需求被切成多段，每段重新加载上下文 | 删除固定身份。需要隔离或第二意见时才临时分身 |
| 总指挥"只调度不代劳"，自己写业务制品即视为"冒顶" | 强模型明明能直接做完，却必须转交 | 删除。主会话可以直接干活 |
| 接管四步 + 身份自检行 + 逐分身强制 `/compact` | 仪式性输出占用上下文；压缩后还要重新加载手册 | 删除。上下文管理交给 DSH 原生压缩 |
| "必须调用专用工具，不允许用通用能力回答" | 工具不可用或不合适时反而卡住 | 技能只提供知识，模型自行判断是否使用 |
| 大量确认点（总计约 59 处），例如范围确认、生成模式确认、档位确认 | 打断连续工作 | 只在不可逆操作处审批（DSH 原生审批），其余由底线兜底 |
| "完整阅读后严格执行"执行手册 | 先读完整手册再动手，消耗大量 token | 技能按需加载，`rk-playbook` ≤150 行 |
| 依赖 openspec / aispec CLI、gate.py、triage.py、GitNexus、API Registry | 环境缺一项就退化或阻塞 | 核心不依赖外部工具；检测到 `openspec/` 时**可选**导入 tasks.md |

## 5. 设计判断：AiDO 的分级 vs RefactorKit 的分级

| | AiDO | RefactorKit |
|---|---|---|
| 依据 | **任务复杂度**（由模型或脚本判断） | ① **模型能力** → 自主度档位（给多少建议）；② **改动风险**（由 diff 事实计算）→ 底线强度 |
| 低档时 | No-SDD：总指挥直接改 | 风险 L0：只需要构建/编译证据 |
| 高档时 | Full-SDD：七分身链路、每步门禁 | 风险 L2：证据 + 仲裁 + 异源审查 + 不可逆操作审批；**过程仍由模型决定** |
| 判定可否被绕过 | 模型可能把复杂改动判成简单（AiDO 用 triage 脚本缓解） | 风险在关闭时按实际 diff 重新计算，自述无效 |

要点：AiDO 用"流程有多重"应对风险，RefactorKit 用"终点检查有多严"应对风险。风险高时检查更严，但不规定过程。

## 6. 与公司 SDD 体系共存（可选兼容）

很多同事已经在用 AiDO 的 OpenSpec 制品。RefactorKit 不替代它，而是**可选读取**：

| 场景 | 行为 |
|---|---|
| 目标仓库存在 `openspec/changes/<id>/tasks.md` | `rk_task_open({ fromOpenspec: '<id>' })` 把未勾选的实现任务导入为契约断言草稿（`trace` 指向任务行），由模型补全验证命令 |
| 任务关闭 | 只在 `.refactorkit/` 中记录；**不回写** tasks.md 勾选（避免与 AiDO apply 技能冲突），报告中列出建议勾选的行 |
| 不存在 `openspec/` | 完全不涉及 |

MVP 不实现此兼容层，列为 P2。

## 7. 对参赛材料的影响

- **真问题**新增一条有力证据：公司自己的 AiDO 在默认的 Lite-SDD 档位中，已经改为由全栈分身"一个上下文做齐，避免跨分身交接损耗"。这说明固定分工的交接成本是实际存在的问题，不是个人感受。
- **真数据**新增对照（规则侧）：

| 指标 | AiDO（实测） | RefactorKit（设计值） |
|---|---|---|
| 提示词总量 | 10 份 / 57,600 字符 / 1,223 行 | 常驻 `rk-playbook` ≤150 行；其余技能按需加载 |
| 重复样板 | 技能下载样板在 9/10 份中重复 | 0（DSH 原生技能发现） |
| 约束方式 | 约 101 处禁令类表述，写在提示词中 | 7 条底线，由代码执行 |
| 用户确认点 | 约 59 处询问 | 仅不可逆操作触发审批 |

> 口径提示：AiDO 一侧为关键词计数，RefactorKit 一侧为设计值，不是同口径实测。路演时应说"量级对比"，不要说"减少了 X%"。
