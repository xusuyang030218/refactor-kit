## 2. 妙计文档四部分

### 2.1 项目基本信息

- **产品名称**（业务场景 + AI 方向）：**老系统现代化重构 · 自主编排 AI 技能插件（RefactorKit）**
- **技术路线**：**C 原子技能（Skill）**

> 路线说明：交付形态是一套原子技能（知识技能 + 视角卡）与原子能力（rk_* 工具）。"自主编排"是这些技能被使用的方式，不是另一个智能体。如果评审更看重 Agent 形态，可以改选 A，第 2.3 节需要相应改写。

### 2.2 30 秒亮作品（≤100 字，[] 内为实测后填写）

> 用 RefactorKit 自主编排技能插件，解决了 AI 重构中"固定分身拖累强模型、AI 自报完成不可信"的痛点，帮助迁移负责人把单个缺口从 [X] 小时降到 [Y] 分钟，并拦下"自报 100%、实测 46.9%"的虚报。

### 2.3 三真

**① 真问题**
- 业务场景：亚信运营商侧有大量 Spring Boot 1.5 / Vue 2 存量系统需要现代化。案例 DTS 老仓库有 8123 个文件、1293 个 Java 文件、146 个 Controller（`truth-report.json` 实测）。
- 一线痛点：
  - AI 自报完成不可信：历史上自报 100%、复查 16%；2026-10-08 实测，自报 100%、加权实测 46.9%。
  - AiDO 固定分身边界硬：7 个分身、278 次会话，约 20% 低效（原汇报数据）。强模型被迫在分身之间搬运上下文。
  - 公司 AiDO 体系自身的佐证：10 份分身提示词共 57,600 字符、1,223 行；技能下载样板在 9/10 份中重复；禁令类表述约 101 处、询问点约 59 处（关键词计数，见 [03 文档](./03-AiDO分身分析与吸收.md)）。其默认的 Lite-SDD 档位已改由全栈分身"一个上下文做齐，避免跨分身交接损耗"，说明交接成本是公司内已被确认的问题。**对外引用这些数字前需确认公司是否允许公开。**
- 为什么适合 AI：读旧代码、写新代码、对照缺口都是大规模阅读与生成工作；但"完成"必须交给另一家模型和真实证据来判定。
- 目标用户：老系统迁移负责人、架构师、QA。

**② 真工具（路线 C：技能名称 + 绑定的原子能力）**

| 技能 | 类型 | 绑定的原子能力 |
|---|---|---|
| `rk-playbook` | 全局地图 | 全部 rk_* 工具 |
| `rk-contract-writing` | 知识 | `rk_task_open`、`rk_gate` |
| `rk-evidence-discipline` | 知识 | `rk_gate`、`rk_task_close` |
| `rk-gap-judgement` | 知识 | `rk_survey`、`rk_gaps`、`rk_truth` |
| `rk-legacy-reading` | 知识 | `rk_delegate`（archaeologist 视角）、`rk_survey` |
| `rk-springboot-1x-to-3x` | 技术栈 | `rk_gate`（unit） |
| `rk-vue2-to-vue3` | 技术栈 | `rk_gate`（build-fe / typecheck） |
| `rk-mybatis-flyway` | 技术栈 | `rk_gate` |
| 视角卡 ×5（skeptic / archaeologist / architect / tester / user-proxy） | 分身视角 | `rk_delegate`、`rk_review` |

原子能力共 11 个：`rk_survey`、`rk_gaps`、`rk_task_open`、`rk_delegate`、`rk_review`、`rk_gate`、`rk_truth`、`rk_task_close`、`rk_next`、`rk_note`、`rk_skill`。说明见设计文档第 8 节。

## 5. 路演金句

- "一个模型写代码、自己说完成，就像让考生自己批卷。RefactorKit 让另一家模型阅卷，再让证据说话。"
- "AiDO 给模型画了 7 个格子；RefactorKit 只画一条终点线。"
- "放开过程，守住结果。"
